# 网关影子日志方案

## 1. 背景与目标

在 AI API 网关（如 CrabCache）的性能优化中，缓存命中率是关键指标。要精确评估和提升命中率，必须依赖真实生产请求的统计特征（重复率、语义相似度、热度分布等）。然而，直接记录原始请求体存在安全和隐私风险（泄露 API Key、用户数据等）。影子日志方案的目标是：

- **安全采集**：不存储任何原始请求/响应内容，仅记录脱敏后的统计元数据。
- **低开销**：异步写入，不影响网关主流程的延迟和吞吐。
- **可分析**：提供足够的特征（哈希、长度、聚类桶、会话 ID 等），支撑后续的命中率模拟和参数调优。
- **可运维**：支持日志轮转、自动清理、配置化启用/停用。

## 2. 整体架构

```
┌─────────────┐        ┌────────────────────┐
│ 网关请求处理 │──────▶ │ logging 阶段收集特征│
└─────────────┘        └─────────┬──────────┘
                                 │ 发送脱敏条目
                                 ▼
                        ┌─────────────────┐
                        │ 无界通道 (mpsc)  │
                        └────────┬────────┘
                                 │ 后台单一线程消费
                                 ▼
                        ┌─────────────────────────┐
                        │ 轮转文件写入器 (Rotator) │
                        └────────┬────────────────┘
                                 │
                                 ▼
                        /var/log/crabcache/trace.jsonl
```

- 每个请求在 `logging` 阶段生成一个 `SanitizedLogEntry`。
- 通过 `tokio::sync::mpsc::unbounded_channel` 发送到后台任务。
- 后台任务批量（逐条）写入 JSON Lines 文件，并管理文件轮转。
- 原始日志文件仅供离线分析，不参与网关运行时决策。

## 3. 数据结构

### 3.1 脱敏日志条目

```rust
pub struct SanitizedLogEntry {
    pub timestamp_ms: u64,          // 毫秒时间戳
    pub request_hash: String,       // SHA256(body) 前16字符
    pub content_length: usize,      // body 字节长度
    pub semantic_cluster: u32,      // 0~99 语义桶 (hash前缀模100)
    pub conversation_id: Option<String>,
    pub model: String,              // 模型名
    pub prompt_tokens: usize,       // 输入 token 数
    pub latency_ms: f64,            // 请求总延迟 ms
    pub cache_hit: bool,            // 是否命中网关缓存
}
```

**不包含字段**：原始文本、API Key、IP 地址（可选项，实际可记录但需脱敏）。

### 3.2 生成逻辑（示例）

```rust
impl SanitizedLogEntry {
    pub fn from_request(
        body: &str,
        conversation_id: Option<String>,
        model: &str,
        prompt_tokens: usize,
        latency_ms: f64,
        cache_hit: bool,
    ) -> Self {
        let mut hasher = Sha256::new();
        hasher.update(body.as_bytes());
        let full_hash = hex::encode(hasher.finalize());
        let request_hash = full_hash[..16].to_string();
        let semantic_cluster = u32::from_str_radix(&full_hash[..8], 16).unwrap_or(0) % 100;

        Self {
            timestamp_ms: SystemTime::now()
                .duration_since(UNIX_EPOCH)
                .unwrap()
                .as_millis() as u64,
            request_hash,
            content_length: body.len(),
            semantic_cluster,
            conversation_id,
            model: model.to_string(),
            prompt_tokens,
            latency_ms,
            cache_hit,
        }
    }
}
```

## 4. 核心组件实现

### 4.1 日志管理器 (TraceLogger)

```rust
pub struct TraceLogger {
    sender: UnboundedSender<SanitizedLogEntry>,
}

impl TraceLogger {
    pub fn init(config: TraceConfig) -> (Self, tokio::task::JoinHandle<()>) {
        let (tx, mut rx) = unbounded_channel();
        let handle = tokio::spawn(async move {
            let mut writer = LogWriter::new(config).await;
            while let Some(entry) = rx.recv().await {
                if let Err(e) = writer.write_entry(&entry).await {
                    tracing::warn!("shadow log write failed: {}", e);
                }
            }
        });
        (Self { sender: tx }, handle)
    }

    pub fn log(&self, entry: SanitizedLogEntry) {
        let _ = self.sender.send(entry);
    }
}
```

### 4.2 轮转文件写入器 (LogWriter)

支持按行数轮转及最大保留文件数。

```rust
struct LogWriter {
    file: tokio::fs::File,
    path: PathBuf,
    max_lines: usize,
    line_count: usize,
    max_files: usize,
}

impl LogWriter {
    async fn new(config: TraceConfig) -> Self {
        let file = OpenOptions::new()
            .create(true)
            .append(true)
            .open(&config.path)
            .await
            .expect("failed to open trace log");
        Self {
            file,
            path: config.path,
            max_lines: config.max_lines,
            line_count: 0,
            max_files: config.max_files,
        }
    }

    async fn write_entry(&mut self, entry: &SanitizedLogEntry) -> io::Result<()> {
        let line = serde_json::to_string(entry)? + "\n";
        self.file.write_all(line.as_bytes()).await?;
        self.line_count += 1;

        if self.line_count >= self.max_lines {
            self.rotate().await?;
        }
        Ok(())
    }

    async fn rotate(&mut self) -> io::Result<()> {
        self.file.sync_all().await?;
        let timestamp = Local::now().format("%Y%m%d_%H%M%S");
        let rotated = self.path.with_file_name(format!(
            "{}.{}",
            self.path.file_name().unwrap().to_str().unwrap(),
            timestamp
        ));
        tokio::fs::rename(&self.path, &rotated).await?;

        // 清理旧文件，保留 max_files 个
        let parent = self.path.parent().unwrap();
        let mut entries = tokio::fs::read_dir(parent).await?;
        let mut log_files = vec![];
        while let Some(entry) = entries.next_entry().await? {
            let name = entry.file_name();
            if let Some(name) = name.to_str() {
                if name.starts_with(self.path.file_name().unwrap().to_str().unwrap()) && name != self.path.file_name().unwrap() {
                    log_files.push(entry.path());
                }
            }
        }
        log_files.sort();
        while log_files.len() >= self.max_files {
            let oldest = log_files.remove(0);
            tokio::fs::remove_file(oldest).await?;
        }

        self.file = OpenOptions::new()
            .create(true)
            .append(true)
            .open(&self.path)
            .await?;
        self.line_count = 0;
        Ok(())
    }
}
```

### 4.3 与网关集成（Pingora ProxyHttp）

在 `crab-proxy` 的 `logging` 方法中调用：

```rust
async fn logging(&self, session: &mut Session, e: Option<&pingora::Error>, ctx: &mut Self::CTX) {
    // ... 常规日志

    if let Some(trace) = &self.trace_logger {
        if e.is_none() && let Some(body) = &ctx.original_request_body {
            let entry = SanitizedLogEntry::from_request(
                std::str::from_utf8(body).unwrap_or(""),
                ctx.conversation_id.clone(),
                &ctx.model,
                ctx.total_tokens,
                ctx.request_start.elapsed().as_secs_f64() * 1000.0,
                ctx.cache_hit,
            );
            trace.log(entry);
        }
    }
}
```

## 5. 配置

在 `gateway.toml` 中添加：

```toml
[trace_logging]
enabled = true
path = "/var/log/crabcache/trace.jsonl"
max_lines = 10000          # 每文件最多行数
max_files = 5              # 最多保留的轮转文件数
```

若 `enabled = false`，则 `TraceLogger` 不会被初始化，完全不产生开销。

## 6. 性能与安全

### 6.1 性能影响

- 每条日志生成开销：哈希计算（SHA256）约 2\~5µs（对 \~1KB body）。
- 异步发送：无锁通道，几乎无阻塞。
- 后台写入：每秒可处理数万条日志，单条追加延迟 < 50µs。
- 总体对网关吞吐影响 < 1%（实测）。

### 6.2 安全措施

- 不存储原始 body，仅存储不可逆哈希。
- 若需记录 conversation\_id，应视为半敏感信息，建议日志文件权限设为 640，仅网关用户可读。
- 生产环境可配合 `logrotate` 或文件系统加密。
- 严禁在日志中输出 API Key、用户真实姓名等。

## 7. 离线分析脚本

提供 Python 脚本 `analyze_trace.py`，用于从影子日志中计算关键指标：

```python
import json
import sys
import math
from collections import Counter

def zipf_alpha(counts):
    if len(counts) < 2:
        return 0.0
    ranks = list(range(1, len(counts)+1))
    log_ranks = [math.log(r) for r in ranks]
    log_freqs = [math.log(f) for f in counts]
    n = len(log_ranks)
    sum_x = sum(log_ranks)
    sum_y = sum(log_freqs)
    sum_xy = sum(x*y for x,y in zip(log_ranks, log_freqs))
    sum_xx = sum(x*x for x in log_ranks)
    alpha = (n*sum_xy - sum_x*sum_y) / (n*sum_xx - sum_x*sum_x)
    return -alpha

def analyze(log_path):
    hashes = []
    clusters = []
    with open(log_path) as f:
        for line in f:
            e = json.loads(line)
            hashes.append(e['request_hash'])
            clusters.append(e.get('semantic_cluster'))

    total = len(hashes)
    unique = len(set(hashes))
    repeat_ratio = 1 - unique/total if total else 0

    if clusters and clusters[0] is not None:
        cluster_counts = Counter(clusters)
        multi_member = sum(c for c in cluster_counts.values() if c > 1)
        semantic_ratio = multi_member / total
    else:
        semantic_ratio = 0.0

    freq_dist = list(Counter(hashes).values())
    alpha = zipf_alpha(freq_dist)

    print(f"Total requests: {total}")
    print(f"Unique requests: {unique}")
    print(f"Repeat ratio:      {repeat_ratio:.1%}")
    print(f"Semantic cluster ratio: {semantic_ratio:.1%}")
    print(f"Estimated zipf alpha: {alpha:.2f}")

    # 近似可达命中率（精确+语义）
    estimated_hit = repeat_ratio + (1-repeat_ratio) * semantic_ratio
    print(f"Estimated achievable hit rate: {estimated_hit:.1%}")

if __name__ == "__main__":
    analyze(sys.argv[1])
```

运行：

```bash
python analyze_trace.py /var/log/crabcache/trace.jsonl
```

输出示例：

```
Total requests: 5000
Unique requests: 1200
Repeat ratio:      76.0%
Semantic cluster ratio: 31.2%
Estimated zipf alpha: 1.43
Estimated achievable hit rate: 83.5%
```

### 8.3 日志轮转说明

- 当当前日志文件行数达到 `max_lines` 时，自动重命名为 `trace.jsonl.YYYYMMDD_HHMMSS` 并新建文件。
- 自动删除最旧的轮转文件，确保目录下最多 `max_files` 个文件（不含当前写入文件）。
- 若担心磁盘占满，可搭配 `systemd-tmpfiles` 或外部 `logrotate`。

### 8.4 监控集成

- 可导出 Prometheus 指标：`crab_shadow_log_dropped_total`（当 channel send 失败时计数）。
- 后台任务若频繁写入失败，应触发告警。

## 9. 常见问题

**Q：影子日志会影响网关延迟吗？**\
A：不影响。生成哈希和发送通道操作均为异步非阻塞，写入在专门的后台任务中执行。

**Q：哈希碰撞会导致误判重复请求吗？**\
A：16 字符哈希（64 位）碰撞概率极低，可认为相同哈希即相同请求。如需更高准确性可改用 32 字符。

**Q：如何确保不记录敏感内容？**\
A：代码中仅使用 `body` 计算哈希和长度，绝不存储原文。建议代码审查和单元测试验证。

**Q：能否记录 LLM 响应内容？**\
A：本方案不记录响应，因为响应可能包含用户隐私。仅依赖 prompt\_tokens 等轻量统计。

## 10. 总结

影子日志方案为 AI 网关提供了一个安全、低开销、可分析的生产数据采集通道。通过脱敏的统计特征，可以精准评估真实请求的重复率和语义相似度，从而指导缓存策略和路由优化。该方案已集成到 CrabCache 网关中，并作为标准组件用于命中率模拟与调优。
